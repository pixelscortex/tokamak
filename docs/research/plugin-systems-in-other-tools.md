# Plugin systems in other tools

Research for TKM-147. Figma coverage is for classic plugins unless stated otherwise.

## Summary

- **Obsidian** uses a local watch build and normally needs a manual reload. Users browse an in-app directory, but the compiled files come from GitHub Releases. Users choose when to update. [Development guide][obs-dev] · [Release guide][obs-release] · [User guide][obs-install]
- **VS Code** packages extensions as VSIX files. In a remote window it picks an extension host using the entry points, install locations and `extensionKind`. The same extension can be installed on the remote host without a separate remote edition. [Publishing][vs-publish] · [Extension host][vs-host] · [Remote SSH][vs-ssh]
- **Raycast** reloads commands on save. It reviews public source submissions in GitHub, distributes built archives through its Store, and updates them automatically. [CLI][ray-cli] · [Publishing][ray-publish] · [Security and distribution][ray-security]
- **Zed** accepts source through a GitHub index and delivers built packages through its gallery. Custom Rust runs as WebAssembly. Installed extensions update on startup by default. [Publishing][zed-publish] · [Package loader][zed-loader] · [Extension development][zed-dev] · [Update settings][zed-settings]
- **Figma** separates document code in a sandbox from UI in an iframe. It can restart a dev plugin after a build. Figma Community distributes releases, and organization admins can make a plugin available to everyone. [Runtime][fig-runtime] · [Quickstart][fig-dev] · [Classic updates][fig-updates] · [Save for everyone][fig-save]
- **Mattermost and Grafana** install on the server once. Mattermost clients fetch enabled JavaScript bundles. Grafana browsers load a plugin's JavaScript when a page needs it and resolve shared frontend libraries from the host. [Mattermost web app][mm-web] · [Grafana lifecycle][graf-life] · [Grafana shared dependencies][graf-deps]

## Obsidian

1. **Setup and loop.** Use Obsidian with a separate test vault, Git, Node with npm, and an editor. Clone the sample into the vault's `.obsidian/plugins/` directory. Run `npm install` and `npm run dev`. The watcher rewrites `main.js` after edits. Disable then re-enable the plugin, or use **Reload app without saving**, to see the change. The guide points to a separate Hot-Reload plugin for automatic reloads. A rebuild alone is not a reload. [First plugin guide][obs-dev] · [Sample build][obs-build]
2. **Package.** Publish a GitHub release with `main.js`, `manifest.json` and optional `styles.css` as separate release assets. The built JS is what users run. The manifest includes `id`, `name`, `version`, `minAppVersion`, `description`, `author` and `isDesktopOnly`. The release tag must match the manifest version. [Release guide][obs-release] · [Manifest][obs-manifest]
3. **Distribution.** Submit the GitHub repository through the Community directory. The directory scans each release, including its manifest, release assets and source, and checks that the build matches. Obsidian also manually reviews popular, featured and flagged plugins. Users turn off Restricted Mode, browse, install and enable. They check for updates and choose what to update. [Submit][obs-release] · [Release checks][obs-manage] · [Security][obs-security] · [Install and update][obs-install]
4. **Runtime and libraries.** The plugin runs in the user's app and can add or manipulate local UI. Obsidian says plugins inherit the app's access level, which can include local files and networking. Its docs show WebView inspection on mobile and Node/Electron access on desktop. I did not find an official description of the exact desktop process boundary. The official build leaves `obsidian`, Electron, Node built-ins and selected CodeMirror and Lezer packages external. The `obsidian` npm package provides types. The React guide installs React and ReactDOM as plugin dependencies; the sample build bundles dependencies outside its external list. [Mobile development][obs-mobile] · [Security][obs-security] · [App UI example][obs-dev] · [Build config][obs-build] · [API types][obs-api] · [React guide][obs-react]

## VS Code

1. **Setup and loop.** Install VS Code, Node.js and Git. The official quickstart uses `npx --package yo --package generator-code -- yo code` to scaffold an extension. Press F5 to start a second VS Code window, the Extension Development Host, with the extension loaded. Save and build changes, then run **Developer: Reload Window** in that host to see them. The quickstart does not promise hot replacement of a running extension. [First extension][vs-dev]
2. **Package and release.** `vsce package` creates a `.vsix`. It packages the runnable extension and its included files. Bundling is optional for typical Node extensions; the web entry needs a single bundle because the web host does not have Node's module loader. `package.json` sets `name`, `publisher`, `version` and `engines.vscode`, plus entry points, contributions and activation rules as needed. Publish to Visual Studio Marketplace or share the VSIX for direct installation. VS Code documents malware and secret scanning, Marketplace signing and client signature verification. It does not describe routine manual review for every release. Marketplace extensions auto-update by default; manually installed VSIX extensions have auto-update disabled by default. [Publishing][vs-publish] · [Manifest][vs-manifest] · [Web extensions][vs-web] · [Marketplace][vs-store] · [Runtime security][vs-security]
3. **Runtime.** Desktop Node extensions use `main` in a local or remote extension host, separate from the editor UI. Web extensions use `browser` in a browser Web Worker without Node APIs. If a remote extension opens a webview, the webview still renders on the user's client; it exchanges messages with the extension. [Extension hosts][vs-host] · [Remote guide][vs-remote] · [Webview API][vs-webview]
4. **Remote Development.** Put `"extensionKind": ["ui"]` in `package.json` when code needs the local machine or local UI host. Use `["workspace"]` when it needs the host holding the workspace. In a desktop remote window this usually means the remote Node host. If both work, `["ui", "workspace"]` prefers local and `["workspace", "ui"]` prefers the workspace host. VS Code can infer placement when the field is missing. Host availability, supported entry points and where the extension is installed also affect selection. A list is a preference, not a request to run both copies. [Extension host selection][vs-host] · [Remote extension guide][vs-remote]
5. **Installing the same extension remotely.** With Remote SSH, open the SSH window first. VS Code installs VS Code Server on that machine. In the Extensions view, select **Install in SSH: [host]** for an eligible extension already on the local machine, or install from the Marketplace in that window and let VS Code pick the location. The local and remote installs are shown separately. For testing or offline installation, package a VSIX and use **Install from VSIX…** in the remote window. `remote.SSH.defaultExtensions` can install a list on each SSH host you connect to. This is placement for a user's remote session, not a general workspace-wide marketplace install. [Remote SSH][vs-ssh] · [Testing remote extensions][vs-remote]
6. **Libraries.** Development uses VS Code typings. At runtime the host supplies the `vscode` module, so the recommended bundle marks it external. Other dependencies travel with the extension, either in the bundle or as packaged production dependencies. Webview HTML loads its own scripts, so use your own React build if you choose React. An extension can expose an API to dependent extensions in the same host; crossing hosts needs a different interface, such as commands. [First extension][vs-dev] · [Bundling][vs-bundle] · [Webviews][vs-webview] · [Remote dependencies][vs-remote]

## Raycast

1. **Setup and loop.** Raycast's getting-started guide lists Raycast 1.26 or later, Node.js 22.14 or later and npm 7 or later. Sign in and run **Create Extension** to scaffold a React/TypeScript project. Run `npm install` then `npm run dev`. The command appears in Raycast. Saving triggers a rebuild and automatic command reload when auto-reload is enabled. Raycast can keep the last built dev extension after you stop the watcher. [Prerequisites][ray-dev] · [First extension][ray-first] · [CLI][ray-cli]
2. **Package and release.** Public publishing submits source to the official `raycast/extensions` repository. Raycast and community reviewers review it. CI validates the manifest, assets, author, build and types. The Store distributes an archived build, which Raycast downloads and unpacks locally. For a local export, `npx ray bundle` creates a `.rayext` ZIP with `package.json` and the built files at the root. The Store security docs describe an archive but do not specify the public Store download suffix. `package.json` describes commands and modes such as `view`, `no-view` and `menu-bar`, plus preferences and platforms. `owner` and `access` cover organization publishing. The Store uses an implicit latest version instead of a manifest version. [Publishing][ray-publish] · [Security][ray-security] · [CLI][ray-cli] · [Manifest][ray-manifest] · [Versioning][ray-version]
3. **Install and update.** Users install from the built-in Store or web Store. Installed extensions update automatically. Raycast checks API compatibility against the installed app and prompts for an app update if needed. Teams can publish a build to a private Store for members. The team guide establishes availability to members, not automatic installation for every member. [Security][ray-security] · [Versioning][ray-version] · [Private Store][ray-teams]
4. **Runtime and libraries.** Raycast runs a managed Node child process locally. Its docs describe a separate V8 isolate and worker thread for each extension, with limited Raycast APIs over RPC. Node file and network access are not further sandboxed by Raycast. A custom React reconciler renders native UI; there is no browser DOM or `react-dom` UI. The npm `@raycast/api` supplies tooling and declarations for authors; the app contains the API runtime and manages Node. Raycast documents build-time dependencies and an `external` list that keeps imports for runtime resolution. React is part of the Raycast runtime: its release notes describe upgrading the React version for extensions as a host change. The official Store source can still list React in `package.json` for development. [Security][ray-security] · [FAQ][ray-faq] · [CLI][ray-cli] · [API runtime][ray-version] · [Manifest][ray-manifest] · [React runtime][ray-react] · [Example manifest][ray-example]

## Zed

1. **Setup and loop.** Use Zed and install Rust via rustup for extensions with Rust code. Zed can install the `wasm32-wasip2` target with rustup. With other Rust installations, make that target available yourself. Zed can also download the WASI SDK to build Tree-sitter grammars. Select **Install Dev Extension** and point Zed at the local source directory. This can replace the installed catalog version for testing. The installer compiles the source, and **zed: rebuild dev extension** recompiles and reloads it on success. Do not assume a Rust source edit will rebuild it on save. [Development guide][zed-dev] · [Actions][zed-actions] · [Install and rebuild source][zed-loader]
2. **Package and release.** The extension's Git repo has `extension.toml` with `id`, `name`, `version`, `schema_version`, `authors`, `description` and `repository`. It can also declare grammars, language servers or capabilities. A submission pins the source as a Git submodule in `zed-industries/extensions` and adds a matching entry and version in `extensions.toml`. A maintainer reviews the PR. The gallery installer downloads and extracts a gzip-compressed tar archive. The Wasm loader looks for built `extension.wasm`; extensions such as themes can contain only declarative assets and need no custom Rust. [Development guide][zed-dev] · [Capabilities][zed-cap] · [Publishing and review][zed-publish] · [Archive loader][zed-loader] · [Wasm loader][zed-wasm]
3. **Install and update.** Users install from Zed's Extension Gallery. Authors submit another index PR to move the pinned source to a new version. Zed auto-updates installed extensions on startup by default. Users can disable updates for individual extensions or choose another version. [Install guide][zed-install] · [Author updates][zed-updates] · [User update settings][zed-settings]
4. **Runtime and libraries.** Rust code is compiled into a WebAssembly component. Zed uses Wasmtime on the host side and exposes functions through WIT bindings in the `zed_extension_api` crate. Other Rust code used by the extension is built into its Wasm artifact. A theme is data that the editor renders; a language extension can locate or download a separate language server executable. The process and download APIs have declared capabilities that Zed can restrict. In SSH remote development the local UI stays local and locally installed extensions are propagated to the remote server so tools such as language servers can run there. [Development guide][zed-dev] · [Wasm host][zed-wasm] · [API implementation][zed-api] · [Languages][zed-languages] · [Capabilities][zed-cap] · [Remote development][zed-remote]

## Figma

1. **Setup and loop.** The classic quickstart uses the Figma desktop app, an editor and, for the TypeScript template, Node/npm, TypeScript and `@figma/plugin-typings`. Plain JavaScript is also an option. Create a local development plugin or import its `manifest.json`. Run it from **Plugins → Development**. In the TypeScript workflow, watch and rebuild on edits. With Figma's hot reload option on, a rebuild restarts the plugin with the latest code. With it off, restart the plugin yourself. [Quickstart][fig-dev] · [Classic plugin development][fig-build]
2. **Package.** The manifest points `main` to runnable JavaScript and optional `ui` to one or more HTML files. It includes a Figma-assigned `id`, API version and supported `editorType` values. `documentAccess` affects how a plugin accesses pages. `networkAccess` specifies allowed domains. The official React example builds `code.js` and inlines the UI script into `ui.html`. The author publishes the development plugin from the desktop app. I did not find a public archive format or a documented client download protocol for published plugins. [Manifest][fig-manifest] · [React sample build][fig-webpack] · [Publish classic plugins][fig-publish]
3. **Install and update.** People can run a plugin from Community or a file and save it for reuse. Figma reviews an initial public submission. The classic plugin guide says approved publishers can publish later code updates without another routine submission; users who installed the plugin get the latest published version, with no version picker to roll back. Private organization publishing skips the public review. Moving private to public requires review. [Use plugins][fig-use] · [Public submission][fig-publish] · [Classic updates][fig-updates] · [Internal plugins][fig-internal]
4. **Runtime and libraries.** The document part runs in a JavaScript sandbox on the main thread. It accesses the document through the injected `figma` API, without the usual browser DOM APIs. For custom UI, `figma.showUI` opens an iframe that has browser APIs. The two parts send messages. These are client runtimes; the standard plugin API does not provide a background server runtime. The typings package only gives development types. The official React example installs React and ReactDOM and bundles them into the iframe UI along with its own code. [Runtime][fig-runtime] · [UI guide][fig-ui] · [Plugin introduction][fig-intro] · [API][fig-api] · [Typings][fig-types] · [React dependencies][fig-react] · [React build][fig-webpack]

## Install once, everyone gets it

### Mattermost: the server pushes notice of a new UI bundle

A system admin installs a plugin on the Mattermost server and enables it. The Marketplace supports install and update from the admin UI. A self-hosted admin can also upload a `.tar.gz` bundle when policy permits. The bundle can contain a manifest, server executables and a built web app bundle. The server component starts as a separate process. [Admin guide][mm-admin] · [Server lifecycle][mm-server]

On activation the server checks the manifest for a web app part, makes the bundled JavaScript available as a static asset, and sends a WebSocket event to connected clients. At startup the web app asks the server for the active web app plugins. It downloads and executes their bundles; it does the same when it receives an activation event. The plugin registers UI components with the Mattermost web app. This applies to the web and desktop clients. The host supplies React, ReactDOM and the JSX runtime for UI that renders inside Mattermost. Members do not install the JavaScript themselves. [Web app loader][mm-web] · [Server lifecycle][mm-server]

### Grafana: browsers fetch the UI when needed

An admin installs the plugin on the Grafana instance through the catalog or an instance configuration. Grafana discovers installed plugins by their `plugin.json`. If there is a backend, Grafana starts the plugin's binary as a separate RPC process. Users open a Grafana dashboard or app page that uses the installed plugin; they do not install a copy in each browser. Installation makes the plugin available on the instance. Access and any required plugin configuration still apply. [Install][graf-install] · [Lifecycle][graf-life] · [Build an app plugin][graf-app]

When a page needs the plugin, the Grafana frontend uses SystemJS to load the plugin's built `module.js` from the instance. SystemJS resolves shared packages such as `@grafana/ui` from Grafana's import map. Authors declare versions for development and externalize the shared packages in their build. At runtime the plugin gets the versions in that Grafana instance. [Lifecycle][graf-life] · [Frontend dependencies][graf-deps]

### Figma: automatic availability, manual invocation

An organization admin can use **Save for everyone** to make a plugin available in members' files. The organization can also publish private plugins. Members find and run the plugin in Figma; saving it for everyone does not normally run it for everyone. For classic plugins, Figma loads the published plugin when it runs and uses the published HTML for the iframe UI when the plugin opens one. The docs explain the manifest and iframe contract, but do not specify when Figma fetches the bytes or how it caches them. This is a precedent for shared availability, alongside the two server-install examples above. [Save for everyone][fig-save] · [Internal publishing][fig-internal] · [Run plugins][fig-use] · [UI API][fig-ui]

## Lessons for Tokamak

These are suggestions for Tokamak, not descriptions of its current behavior.

1. **Make the first plugin easy to write, including with an AI agent.** Offer **Create Plugin** with a tiny manifest and one working server/UI example. Let an agent write those files directly. Give the app or a single dev command a built-in TypeScript compiler, file watcher and clear build errors. Reload only the changed part on a successful build; keep the last working build if compilation fails. Raycast and Figma show how far a template and reload loop can go. A managed compiler removes setup, but Tokamak must maintain it. An optional CLI can serve larger plugins without making it the first step. [Raycast first extension][ray-first] · [Figma quickstart][fig-dev]
2. **Install and activate once per workspace.** Make the server the source of truth for enabled plugin IDs and exact versions. Have the window request that list when it connects, subscribe to changes, and fetch the matching UI build by content hash. Show commands from the list right away; load UI only when opened. Use Mattermost's notification model and Grafana's lazy loading. Key cached assets by server/workspace and release so changing servers cannot reuse the wrong build. Activate matching server and UI versions together; let admins pin and roll back. This adds synchronization work, but clients never need to manage separate installs. [Mattermost loader][mm-web] · [Grafana lifecycle][graf-life]
3. **Give local execution its own boundary.** Use distinct `server` and `ui` entries. Add a `local` entry only for plugins whose tasks must run on a person's machine. Prefer a small set of host operations exposed through typed messages, such as opening a configured local tool with validated arguments. Make the user grant local execution per plugin and workspace. Keep the browser UI away from unrestricted Tauri commands and keep local grants separate from a server administrator's install. If a fixed set of operations is too narrow, run optional local code in a separate worker with explicit capabilities. Separate entries take more contracts and tests, but a workspace update need not gain new local access silently. VS Code offers a placement precedent; its `extensionKind` list chooses one host. Zed offers a precedent for restricting executable access. [VS Code placement][vs-host] · [Zed capabilities][zed-cap]
4. **Provide Solid, the SDK and UI kit at runtime.** Reserve stable import names and resolve them from Tokamak in each supported runtime. Use a frontend import map or a loader in the plugin's UI frame. Provide server SDK functions through the server runtime. Ship types with the author template and let Tokamak compile simple plugins without a package install. Allow larger plugins to bundle their own unrelated dependencies. Require a supported SDK or UI API range in the manifest and check it before activation. Sharing one copy keeps the host and plugin on the same runtime, but Tokamak takes on compatibility work. Bundling everything gives authors more version freedom at the cost of larger builds and duplicate runtime state. [Grafana dependency linking][graf-deps] · [Obsidian build][obs-build] · [Raycast API versioning][ray-version]
5. **Use a catalog with immutable builds.** Start with a private workspace catalog and signed package upload; add a curated public catalog if demand warrants it. A release can reference a GitHub source commit for review and provenance, while the catalog delivers a signed, versioned build. Show publisher, compatibility and requested permissions before activation. Consider automated checks on every release, review for public listings, and explicit approval when permissions expand. Let administrators choose a pinned version or an update channel. The catalog adds operations and review work; direct source URLs are easier to accept but shift validation and discovery to users. Keep development folder imports separate from published installs. [VS Code signing][vs-security] · [Raycast review and delivery][ray-security] · [Figma private distribution][fig-internal] · [Obsidian release checks][obs-manage]
