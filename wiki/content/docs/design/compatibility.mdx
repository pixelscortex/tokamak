---
title: DOM compatibility
description: What the client needs before DOM-dependent UI libraries such as ui-sdk can run on it.
---

The goal is to run ui-sdk's behaviours on our renderer without moving to a
webview. This page is the working list: each row is a browser API a library
expects, where we stand, and what kind of work closes it. Update a row when its
status changes.

The "uses" column counts how often `@ui-sdk/core` 0.1.0-beta.6 refers to the
API in its 388 built files. It is a rough measure of how much depends on a row,
taken with a text search, not a guarantee that every use matters.

## Status words

- **Have:** works today.
- **Wiring:** JavaScript only. Our renderer already owns the tree, so the
  answer can be computed in QuickJS.
- **Bridge:** needs a call into Rust and back. Blitz may already hold the
  answer.
- **Engine:** needs Blitz itself to do something it may not do today.
- **Unchecked:** nobody has looked yet.

## Solid

`@ui-sdk/solid` requires Solid 2 and `@solidjs/web`. The client is on Solid
1.9 with the universal renderer. Two ways through, neither chosen:

- Move the client to Solid 2 and make the adapter render through our renderer.
- Write a small adapter of our own from `@ui-sdk/core` primitives to our Solid
  1.9 renderer. The core is written to be rendered by any framework.

## Order of work

1. Prove the idea on one behaviour: a menu with roving focus, opened beside a
   button. It touches the tree, events, focus, measurement and a popup, so it
   shows which rows are real.
2. Close the **Wiring** rows; they need no Rust change.
3. Close focus by script. Most other behaviours wait on it.
4. Close measurement, then popups.
5. Re-run the count against the installed version and fill in the
   **Unchecked** rows.
